## ひとことで

AI コーディングは、プログラムを書く・直す・テストする・レビューする作業を AI に手伝わせる、または任せることです。数年前は「次の 1 行を予測して補う」道具でしたが、いまは「この不具合を直して」と頼むと、自分でコードを読み、修正し、テストを走らせて結果まで報告する [AI エージェント](topic:agents) が主流になっています。

## 仕組みをかんたんに

土台は、大量のプログラムと文章で学んだ大規模言語モデル（LLM）です。これに次のような道具を持たせています。

- **ファイルを読む・書く**: プロジェクトの中を探して、関係する場所を見つけます。
- **コマンドを実行する**: テストやビルド（プログラムを組み立てる作業）を走らせ、エラーが出たら読んで直します。
- **手順書を読む**: リポジトリ（プログラムの保管場所）に置かれた「このプロジェクトでの決まり」を読んでから作業します。

使い方は大きく 3 つあります。エディタの中で提案を受ける「補完型」、エディタやターミナル（文字で操作する画面）で対話しながら作業させる「対話型」、課題を渡して裏で作業させ、終わったら変更案（プルリクエスト）を出させる「お任せ型」です。

## いま何が起きているか

- **日常の道具になった**: 開発ツール会社 JetBrains が 2026 年 8 月に公表した調査では、プロの開発者の大半が週に 1 回以上 AI コーディングエージェントを仕事で使っていると報告されています。
- **主役が入れ替わった**: 同じ調査では、職場で使われている道具として Anthropic の Claude Code が最も多く、OpenAI の Codex も急速に伸びた一方、以前の定番だった GitHub Copilot や Cursor は比率を下げたとされています。補完型から、作業をまとめて任せられるエージェント型へ関心が移ったことの表れです。
- **「書く」より「確かめる」が仕事に**: AI が書くコードの量が増えたぶん、人の仕事はレビュー、設計、テストの用意、要件をはっきりさせることに寄っています。
- **開発者以外も作り始めた**: 業務担当者が言葉で頼んで小さな社内ツールを作る、いわゆる「バイブコーディング」（雰囲気で指示して作らせる開発）も広がっています。手軽な反面、保守や安全性の確認が置き去りになる問題も指摘されています。

## どう使われているか

| 使い方 | 誰が・どこで | 何が良くなるか |
| --- | --- | --- |
| 不具合の調査と修正 | 開発チーム | 原因探しの時間が減り、修正案とテストがセットで出てくる |
| テストコードの作成 | 開発・品質保証 | 手薄だったテストを短時間で厚くできる |
| 古いシステムの読み解き | 保守担当・情報システム部門 | 担当者が辞めたプログラムの説明書を作らせられる |
| コードレビューの一次チェック | チームリーダー | 見落としやすい誤りを先に指摘させ、人は設計に集中できる |
| 社内ツール・業務の自動化 | 事務・現場の担当者 | Excel マクロや小さな Web ツールを自分で作れる |
| 言語・フレームワークの移行 | 開発チーム | 古い書き方から新しい書き方への機械的な書き換えを任せられる |

## ビジネスへの応用

- [ソフトウェア開発・IT](industry:software): 開発の生産性向上の中心。少人数のチームで扱える範囲が広がる。
- [バックオフィス・士業](industry:backoffice): 定型の集計や転記を自動化する小さなツールを、担当者自身が作る。
- [製造業](industry:manufacturing): 設備や検査装置まわりの古い制御・集計プログラムの読み解きと保守。
- [金融・保険](industry:finance): 古い基幹システムの解析や移行の下準備（厳しいレビュー体制が前提）。
- [マーケティング・営業](industry:marketing): データ集計やレポート作成の自動化、ランディングページの試作。
- [自治体・公共](industry:public): 庁内の定型作業を自動化するツールづくり（調達・セキュリティ規程の確認が先）。

## 始め方と費用感

1. **既製サービスで試す**: 個人向け・チーム向けの有料プランは、2026 年時点で 1 人あたり月数千円〜数万円程度です。重い使い方ほど上位プランや従量課金が必要になります。まずは小さな不具合修正やテスト作成から始めます。
2. **自社のコードと決まりを読ませる**: リポジトリに「このプロジェクトの決まり」（コーディング規約、テストの回し方、触ってはいけない場所）を書いたファイルを置くと、品質が目に見えて安定します。
3. **作り込む**: 課題管理システムから自動で作業させる、レビューを自動化する、など開発の流れに組み込みます。社内の情報を外に出せない場合は、契約条件の確認や、[オープンモデル](topic:open-models) を自社環境で動かす選択肢もあります。

## 注意点・リスク

- **もっともらしい誤り**: テストが通っても、要件を取り違えていることがあります。仕様の確認とレビューは人が行います。
- **セキュリティ**: 秘密の鍵やパスワードをコードに書いてしまう、危ないコマンドを実行する、といった事故がありえます。実行できる操作を絞り、重要な環境には直接触らせない設定にします。
- **ライセンスと機密**: 生成されたコードの扱い、ソースコードを外部サービスに送ってよいかを社内で決めておきます。
- **保守できない量のコード**: 簡単に書けるぶん、誰も理解していないコードが増えがちです。「人が説明できないコードは入れない」などの線を引きます。
- **技能の空洞化**: 若手が基礎を学ぶ機会が減る懸念もあります。教育の場では、AI の出力を説明させる練習を組み合わせます。
